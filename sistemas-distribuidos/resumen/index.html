01

Modelo distribuido y decisiones de diseño

Un sistema distribuido coordina computadoras autónomas mediante mensajes para ofrecer un resultado común. El punto de partida no es memorizar arquitecturas, sino entender qué cambia cuando no hay memoria, reloj ni destino de fallo compartidos, y qué decisiones compensan esas limitaciones.

Qué hace distribuido a un sistema

Sistema distribuido, Tanenbaum. Colección de computadoras independientes que el usuario ve como un solo sistema coherente.
Sistema distribuido, Coulouris. Sistema de computadoras interconectadas por una red que se comunican y coordinan sus acciones intercambiando mensajes.
Sistema distribuido, Lamport. Aquel en el que el fallo de una computadora que ni siquiera sabías que existía puede dejar inutilizable la tuya.

No son tres redacciones intercambiables. Cada una fija una dimensión que se usa durante toda la materia:

  • Tanenbaum, transparencia: las computadoras son autónomas por dentro, pero la distribución se presenta como un sistema coherente.
  • Coulouris, mecanismo: la coordinación ocurre por mensajes sobre una red, no mediante memoria global.
  • Lamport, fallo parcial: una dependencia remota puede fallar mientras el resto sigue ejecutando, incluso si quien usa el sistema desconoce esa dependencia.

De la autonomía aparecen los problemas centrales de la materia:

  • No hay memoria global: dos nodos pueden observar versiones diferentes de un dato.
  • No hay reloj global perfecto: los timestamps físicos no bastan para reconstruir causalidad.
  • La red demora, reordena, duplica o pierde: un timeout no permite distinguir un nodo caído de una respuesta lenta.
  • Hay fallos parciales: una parte puede funcionar mientras otra falla. El sistema debe decidir con información incompleta.
  • La concurrencia es inevitable: varios participantes operan sobre recursos relacionados sin un orden total natural.
Distribuir compra capacidad, cercanía geográfica y aislamiento de fallos, pero se paga con coordinación. Conviene distribuir solo aquello cuyo beneficio supera ese costo.

Transparencia, con alcance explícito

Decir que un sistema es transparente sin aclarar qué oculta es incompleto. Las dimensiones clásicas son:

  • Acceso: la operación se expresa igual aunque el recurso sea local o remoto.
  • Ubicación: el nombre no revela la dirección física.
  • Migración y relocalización: el recurso puede moverse, incluso mientras se usa, sin cambiar cómo se lo referencia.
  • Replicación: el cliente no elige ni coordina copias.
  • Concurrencia: varios usuarios comparten recursos sin romper invariantes.
  • Fallo: ciertos fallos se enmascaran mediante redundancia o reintentos.
  • Persistencia: se usa igual un objeto temporal que uno reconstruido desde almacenamiento.
La transparencia total no siempre es deseable. Fingir que una llamada remota es local oculta latencia, serialización y ambigüedad ante fallos. Una buena abstracción simplifica el caso normal, pero deja visibles las diferencias que el programa necesita manejar.

Apertura e interoperabilidad

Un sistema abierto publica la sintaxis y la semántica de sus interfaces. Interoperabilidad significa que implementaciones diferentes cooperan. Portabilidad significa que una aplicación puede cambiar de implementación con pocos cambios. Una URL pública no alcanza: también deben estar definidos tipos, errores, compatibilidad, autenticación, orden y semántica de reintentos.

Cómo usar los parámetros en un ejercicio

  1. Fijar requisitos medibles: carga, latencia, disponibilidad, consistencia, recuperación y costo.
  2. Encontrar el recurso limitante y el dominio de fallo.
  3. Elegir un mecanismo para cada requisito, explicando qué sacrifica.
  4. Dibujar componentes, flujos, almacenamiento y límites de responsabilidad.
  5. Recorrer fallos concretos: mensaje perdido, duplicado, nodo lento, caída durante una escritura y partición de red.
Si una venta no puede descontar stock dos veces, “usar una cola” no resuelve por sí solo el requisito. Hay que explicar quién conserva el estado, cómo identifica duplicados, dónde ocurre la operación atómica y qué sucede si el consumidor cae después de guardar pero antes de confirmar el mensaje.

Centralización, distribución y descentralización

Centralizado. Un componente concentra una decisión o un recurso crítico.
Distribuido. El cómputo o los datos viven en más de una computadora.
Descentralizado. Ningún participante tiene control exclusivo y la decisión emerge de la coordinación entre pares.

Distribuido no implica descentralizado: puede haber cien workers gobernados por un único coordinador. Tampoco centralizado implica una sola máquina: un servicio lógico central puede estar replicado. La pregunta útil es qué autoridad, estado o flujo queda concentrado y qué ocurre si deja de estar disponible.

FormaVentajaRiesgoCuándo conviene
Control centralDecisiones simples y observablesCuello de botella o único dominio de falloEscala acotada, coordinación fuerte
JerarquíaAgrega y delega por nivelesLos niveles altos siguen siendo críticosGeografía, agregación, organizaciones grandes
ParesElimina autoridad únicaDiscovery, consenso y seguridad difícilesParticipantes autónomos o alta distribución

Las topologías expresan quién puede comunicarse directamente: estrella simplifica administración pero concentra tránsito; árbol escala agregación pero depende de sus ancestros; anillo limita conexiones pero aumenta el camino; malla ofrece rutas alternativas a mayor costo; bus comparte medio y contención; pipeline encadena etapas con dependencias claras.

Ley de Conway: la arquitectura de un sistema tiende a copiar la estructura de comunicación de la organización que lo construye. Si dos equipos no pueden coordinar cambios, una frontera de servicio entre ellos necesita un contrato mucho más estable que una frontera dentro del mismo equipo.

02

Concurrencia y comunicación local

Antes de distribuir entre máquinas hay que dominar los mismos problemas dentro de una: intercalaciones, exclusión, espera y comunicación. La red cambia los mecanismos disponibles, pero no elimina las invariantes que deben preservarse.

Threads, procesos y computadoras

Concurrencia. Varias actividades progresan durante el mismo intervalo y sus eventos pueden intercalarse, incluso sobre un único procesador.
Paralelismo. Varias actividades ejecutan simultáneamente sobre recursos físicos distintos.
ModeloMemoriaComunicaciónAislamiento
MultithreadingCompartida dentro del procesoVariables y primitivas de sincronizaciónBajo, un fallo puede afectar todo el proceso
MultiprocessingPrivada por proceso en una máquinaIPC del sistema operativoMayor, con costo de cambio y copia
MulticomputingPrivada por nodoMensajes por redFísico, con fallos parciales

Concurrencia significa que varias actividades progresan con posibles intercalaciones. Paralelismo significa que dos actividades ejecutan simultáneamente sobre recursos distintos. Puede haber concurrencia en un solo core y paralelismo entre tareas que nunca comparten estado.

Safety, liveness y atomicidad

Propiedad de safety. Algo malo nunca ocurre, por ejemplo dos procesos nunca ocupan juntos una sección crítica.
Propiedad de liveness. Algo bueno finalmente ocurre, por ejemplo todo proceso que espera termina entrando.

Una operación es atómica cuando los demás observan que ocurrió completa o no ocurrió. Una sección crítica agrupa operaciones que deben verse como una unidad respecto de un recurso compartido.

Los algoritmos de exclusión puramente por software, como Peterson para dos participantes, dependen de lecturas y escrituras atómicas y de un modelo de memoria específico. En hardware moderno se usan instrucciones de lectura, modificación y escritura como compare and swap:

CAS(direccion, esperado, nuevo):
    atomico:
        anterior = *direccion
        if anterior == esperado:
            *direccion = nuevo
        return anterior

lock:
    while CAS(estado, LIBRE, OCUPADO) != LIBRE:
        esperar_o_ceder_cpu()
Un spinlock preserva exclusión, pero puede desperdiciar CPU y sufrir starvation. Corrección no implica buen rendimiento ni equidad.

Primitivas de sincronización

  • Mutex: exclusión con propiedad de dueño. Quien lo adquiere debe liberarlo.
  • Semáforo: contador atómico. wait decrementa o bloquea; signal incrementa y puede despertar a alguien. El binario sirve como exclusión, el contador representa unidades disponibles.
  • Monitor: encapsula estado, operaciones y exclusión. Solo un thread ejecuta dentro del monitor.
  • Condition variable: permite dormir hasta que un predicado sea verdadero. Se verifica con while, porque el estado puede cambiar antes de recuperar el lock.
  • Barrera: ningún participante cruza hasta que llegan los N esperados.
  • Rendezvous: dos actividades se encuentran en un punto y ambas esperan a la otra.
consumir():
    lock(m)
    while cola.vacia():
        not_empty.wait(m)
    item = cola.pop()
    not_full.signal()
    unlock(m)
    return item

Problemas clásicos

Productor consumidor requiere exclusión sobre el buffer, espera si está vacío y, si es acotado, espera si está lleno. Lectores escritores permite lectores simultáneos pero excluye escritores; priorizar siempre a un grupo puede dejar al otro sin progreso. Filósofos comensales muestra deadlock si todos retienen un recurso mientras esperan el siguiente.

Deadlock. Conjunto de actividades que esperan circularmente recursos retenidos por otras del mismo conjunto.

Un grafo wait for dibuja una arista de Pi a Pj cuando Pi espera un recurso retenido por Pj. Un ciclo indica posibilidad de deadlock. Las condiciones de Coffman son exclusión mutua, retención mientras se espera, ausencia de desalojo y espera circular. Romper cualquiera evita ese tipo de deadlock. Ordenar globalmente la adquisición de locks rompe la espera circular.

TCP, UDP y sockets

El modelo TCP/IP organiza responsabilidades en enlace, Internet, transporte y aplicación. El modelo OSI agrega presentación y sesión como capas conceptuales separadas. Encapsular significa que cada capa agrega su header y trata el contenido superior como payload.

TCPUDP
AbstracciónStream de bytes bidireccionalDatagramas
GarantíasEntrega ordenada sin duplicados mientras la conexión sea válidaMejor esfuerzo, puede perder, duplicar o reordenar
ControlConexión, retransmisión, flujo y congestiónLa aplicación agrega lo que necesite
Uso típicoCuando importa completar un flujoTiempo real, multicast, consultas breves o protocolo propio

TCP no conserva fronteras de mensaje. Un send no corresponde a un recv. La aplicación necesita framing: longitud fija, delimitador escapable, prefijo de longitud o combinación de header fijo y payload variable.

servidor TCP:
    s = socket()
    bind(s, ip, puerto)
    listen(s)
    while true:
        c = accept(s)
        atender(c)       # recv puede devolver menos bytes que los pedidos

cliente TCP:
    c = socket()
    connect(c, ip, puerto)
    send_all(c, frame(request))
    response = read_frame(c)

Una comunicación sincrónica bloquea el progreso lógico hasta recibir respuesta. Una asincrónica desacopla la aceptación del pedido de su resultado. Esto es independiente de que la API del socket bloquee un thread: se puede implementar un protocolo asincrónico con sockets bloqueantes y threads, o uno sincrónico con I/O no bloqueante.

Health check por UDP o TCP

UDP conviene para heartbeats frecuentes cuando cada datagrama es autocontenido, perder alguno es aceptable, el estado más nuevo reemplaza al anterior y se quiere evitar una conexión por cliente. Cada mensaje lleva versión, identidad, secuencia y timestamp; el receptor declara sospecha recién después de varias ausencias. TCP conviene si hay una sesión existente, importa recibir cada cambio ordenado o la cantidad de clientes permite mantener conexiones.

UDP no confirma que la aplicación remota procesó. TCP tampoco prueba salud de negocio solo porque la conexión siga abierta. Un health check útil valida la capacidad que se quiere enrutar, con deadline y sin depender circularmente del componente observado.

Flujo y congestión

El control de flujo evita saturar al receptor. El control de congestión evita saturar la red. Si productores ilimitados alimentan consumidores más lentos, siempre hace falta una política de backpressure: bloquear, rechazar, descartar, muestrear, degradar calidad o persistir hasta un límite. Una cola sin límite solo transforma sobrecarga en agotamiento de memoria y latencia creciente.

Al comparar modelos, nombrá la memoria compartida, el mecanismo de comunicación, el aislamiento y el tipo de fallo. Al diseñar sobre TCP, explicá framing, lecturas parciales, timeouts y qué representa el cierre de conexión.
03

Paralelización y arquitectura física

Paralelizar no es “agregar máquinas”. Primero se descompone el trabajo, se cuantifica el camino crítico y recién después se elige una arquitectura física. Los nombres y diagramas completan el diseño: permiten localizar componentes sin acoplarse a su ubicación y comunicar con precisión cómo se despliegan.

Descomponer trabajo

Una tarea se divide de dos formas básicas:

  • Descomposición funcional: etapas diferentes realizan transformaciones distintas. Produce pipelines y especialización.
  • Particionamiento de datos: workers equivalentes procesan subconjuntos del input. Produce paralelismo de datos.

Los patrones frecuentes son master worker, pipeline, divide and conquer, map reduce, work pool y DAG. Para elegir hay que identificar dependencias, granularidad, balance de carga, volumen que cruza la red y estado compartido.

Camino crítico. Cadena de dependencias con mayor duración. Ninguna cantidad de procesadores puede reducir la ejecución por debajo de ese camino.

Amdahl, Gustafson y Work Span

Si una fracción P del tiempo original es paralelizable y se usan N procesadores, la ley de Amdahl estima:

Speedup_Amdahl(N) = 1 / ((1 - P) + P/N)
Limite cuando N tiende a infinito = 1 / (1 - P)
Con P = 0.90, ni infinitos procesadores superan un speedup de 10. Con 10 procesadores, el speedup ideal es 1 / (0.1 + 0.9/10) = 5.26.

Amdahl mantiene fijo el tamaño del problema. Gustafson observa que, al crecer los recursos, suele crecer el trabajo útil y mantiene aproximadamente fija la duración:

Speedup_Gustafson(N) = N - alpha * (N - 1)
alpha = fraccion serial medida en la ejecucion paralela

El modelo Work Span separa:

  • T1, work: tiempo con un procesador, suma de todo el trabajo.
  • Tinf, span: tiempo con procesadores infinitos, duración del camino crítico.
  • Paralelismo disponible: T1 / Tinf.

Con P procesadores, el tiempo ideal satisface TP >= max(T1/P, Tinf). En la práctica se suman comunicación, sincronización, scheduling y desbalance. Una tarea demasiado fina pierde más en overhead que lo que gana al paralelizarse.

Partición y balance

Una partición estática es barata si el costo por elemento es uniforme. Si es irregular, una cola dinámica de tareas mejora utilización, aunque agrega coordinación. El objetivo no es repartir la misma cantidad de elementos, sino aproximar el mismo tiempo de trabajo.

particion estatica:
    worker i procesa rango(i)

work pool dinamico:
    mientras haya tareas:
        worker libre toma siguiente tarea atomica

La granularidad determina cuántas oportunidades de paralelismo hay y cuánto cuesta coordinarlas. Agrupar tareas reduce overhead, pero puede empeorar balance y recuperación. El dato debe quedarse cerca del cómputo cuando moverlo es más caro que procesarlo.

Arquitecturas de procesamiento

La taxonomía de Flynn clasifica por cantidad de flujos de instrucciones y de datos:

Un flujo de datosMúltiples flujos de datos
Una instrucciónSISD, procesador secuencialSIMD, misma operación sobre muchos datos
Múltiples instruccionesMISD, raro, pipelines redundantesMIMD, cores o nodos autónomos

En un multiprocessor, varios procesadores comparten memoria:

  • SMP: procesadores simétricos ejecutan el mismo sistema operativo y acceden a los recursos con los mismos roles.
  • AMP: procesadores con roles distintos, por ejemplo uno controla I/O y otros computan.
  • UMA: latencia aproximadamente uniforme a toda la memoria.
  • NUMA: cada procesador tiene memoria cercana más rápida y accede a memoria remota con mayor costo.

En un multicomputer, cada nodo tiene memoria privada y se conecta por red. Escala capacidad y dominio físico, pero cualquier dato compartido debe convertirse en mensajes, replicación o almacenamiento remoto.

MIMD, multiprocessor contra multicomputer. En ambos hay múltiples flujos de instrucciones y datos. Un multiprocessor comparte memoria o reloj de hardware; un multicomputer está formado por computadoras completas sin memoria ni reloj compartidos. Un sistema distribuido pertenece a esta segunda familia.
NUMA tiene espacio de direcciones compartido, aunque el costo dependa de la ubicación. Multicomputing no tiene memoria compartida de hardware. Esa diferencia determina el modelo de programación.

Nombres, direcciones y discovery

Nombre. Identificador lógico de una entidad.
Dirección. Información que permite alcanzarla en una ubicación o transporte.
Direccionamiento. Mapeo entre el nombre estable de una entidad y una dirección que puede cambiar o reutilizarse.

Separarlos permite mover, replicar o reemplazar una entidad sin cambiar a sus consumidores. La resolución transforma nombre en una o más direcciones y puede incluir versión, salud, prioridad y balanceo.

DNS es jerárquico y distribuido: resolvers consultan servidores raíz, de dominio superior y autoritativos, con caches gobernadas por TTL. Un registro A o AAAA da una dirección, CNAME un alias, MX un destino de correo y SRV puede expresar servicio, puerto, prioridad y peso.

Service discovery adapta la idea a instancias efímeras:

  • Registro: cada instancia o un controlador publica su endpoint y metadata.
  • Health check y lease: las entradas vencen o se eliminan si la instancia deja de renovar.
  • Descubrimiento del lado cliente: el cliente consulta el registro y elige instancia.
  • Descubrimiento del lado servidor: un proxy o balanceador resuelve y enruta.
El nombre establece identidad. La dirección expresa una decisión de despliegue. Acoplar ambos hace que cada migración se convierta en un cambio de contrato.

Qué debe mostrar cada diagrama

  • Casos de uso: actores externos, objetivos que obtienen del sistema y relaciones include, extend o generalización cuando realmente aclaran reutilización.
  • Paquetes: agrupaciones lógicas y dirección de dependencias. Sirve para detectar ciclos y capas que conocen demasiado.
  • Actividad: acciones, decisiones, forks y joins. Modela flujo de control, no máquinas físicas.
  • Componentes: piezas reemplazables, interfaces provistas y requeridas. Explica contratos, no la secuencia temporal.
  • Secuencia: lifelines y mensajes ordenados de arriba hacia abajo. Debe incluir respuestas, alternativas, loops y operaciones asincrónicas relevantes.
  • Despliegue: nodos físicos o entornos de ejecución y artefactos instalados. Acá se ven réplicas, zonas y protocolos.
  • Robustez: boundary recibe interacción, control coordina el caso de uso y entity conserva información del dominio. El flujo normal es actor, boundary, control, entity, sin que una entity conozca la interfaz.
  • DAG: tareas como nodos y dependencias de datos como aristas. Una arista A a B significa que B no puede ejecutar hasta disponer del resultado de A.

04

Protocolos e invocación remota

Esta sección concentra las decisiones que permiten que dos componentes se entiendan: separación lógica y física, contratos, protocolo de mensajes y abstracciones de invocación. Cliente servidor, REST, RPC y objetos distribuidos se comparan acá como alternativas completas, sin anticipos en otros capítulos.

Layers y tiers

Layer. División lógica de responsabilidades. Cada capa ofrece servicios a la superior y usa servicios de la inferior.
Tier. Unidad física de despliegue. Indica en qué proceso o máquina corre una parte.

Presentación, negocio y persistencia pueden ser tres layers dentro de un único ejecutable, o desplegarse en tres tiers. Cambiar layers mejora modularidad. Cambiar tiers modifica latencia, seguridad, escalabilidad y fallos.

Un modelo lógico frecuente separa Presentation y API como entradas, Services como coordinación de casos de uso, Core Business como reglas y entidades, y Persistence como acceso a datos. Security y Audit son responsabilidades transversales. En un despliegue 3 tier, el cliente corre presentación, un servidor ejecuta negocio y otro aloja la base. Los layers no deben confundirse con esas máquinas.

Una dependencia normal baja desde una capa de mayor nivel hacia una abstracción de menor nivel. Un upcall permite que una capa inferior notifique a una superior mediante callback, evento o interfaz invertida. Si dos layers se conocen mutuamente por sus implementaciones aparece dependencia circular, que dificulta probar y reemplazar.

“Arquitectura de tres capas” no dice cuántas máquinas hay. “Arquitectura de tres tiers” sí afirma una separación de despliegue, pero no prueba que cada tier tenga una sola responsabilidad lógica.

Interfaces y contratos

Interfaz. Frontera pública que permite comunicar componentes, servicios o sistemas mediante un contrato, ocultando la implementación privada.

Una interfaz lista operaciones accesibles. Un contrato además fija precondiciones, postcondiciones, invariantes, tipos, errores y semántica observable. En una interfaz remota también debe definir:

  • identidad y versionado de recursos;
  • autenticación, autorización y límites de uso;
  • timeouts esperados y cancelación;
  • idempotencia y deduplicación;
  • orden, consistencia y visibilidad de escrituras;
  • compatibilidad hacia atrás de consumidores y productores.

Un contrato orientado a entidades expone recursos y cambios de estado. Uno orientado a procesos expone acciones o procedimientos. Ninguno es universalmente mejor: entidades favorecen una interfaz uniforme y procesos modelan operaciones de negocio complejas sin fingir que todo es CRUD.

Orientados a entidades: GET /users/{id} y POST /products. Orientados a procesos: POST /search y POST /transform/html-to-pdf. El primero identifica sustantivos y usa la operación estándar; el segundo nombra una acción cuyo resultado no se modela naturalmente como CRUD.

Las interfaces también se clasifican por alcance: Web API con HTTP, API remota custom sobre TCP o UDP, API orientada a procedimientos como gRPC, API orientada a objetos como CORBA o RMI, biblioteca o framework dentro del proceso, y API de sistema operativo como POSIX o WinAPI.

Qué define un protocolo

Protocolo. Acuerdo sobre formato, significado, orden y temporización de mensajes entre participantes.

La sintaxis indica campos y codificación. La semántica indica qué significa cada valor y qué efecto produce. La secuencia indica qué mensajes son válidos en cada estado. La temporización define timeouts, retransmisiones y vigencia.

Cada capa intercambia una PDU compuesta por control propio y payload de la capa superior. Al enviar, las capas encapsulan. Al recibir, desencapsulan y validan.

PDU. Unidad de datos que un protocolo entrega a la capa inferior para ser encapsulada.

Si una PDU supera el máximo inferior, se segmenta y cada fragmento repite headers. Si varias PDUs pequeñas caben juntas, batching amortiza headers a costa de esperar y sumar latencia. El protocolo de aplicación debe conocer qué garantiza la capa inferior: una imagen grande sobre UDP puede perderse completa por faltar un solo fragmento.

Dos protocolos para el mismo registro

Para {email: string, nacimiento: date}, una alternativa textual es una línea JSON en UTF-8 terminada por salto:

{"email":"ana@example.com","nacimiento":"2001-04-23"}\n

Es legible y extensible, pero el delimitador debe respetar strings escapados y el parseo cuesta más. Una alternativa binaria usa header fijo y campos con longitud:

version:u8 | email_len:u16 | email:bytes | dias_desde_epoch:i32

Es compacta y determinista, pero necesita acordar endianness, encoding, rango de fecha y evolución. Ejemplos no binarios conocidos son HTTP en su forma textual, JSON y SMTP. Protocolos o formatos binarios incluyen Protocol Buffers, MessagePack y las capas binarias modernas de HTTP/2.

Cliente servidor y peer to peer

Cliente servidor. El cliente inicia pedidos y el servidor escucha, procesa y responde. El rol describe una interacción, no necesariamente una máquina permanente.

Ventajas: autoridad y estado fáciles de ubicar, clientes simples, seguridad y operación centralizadas. Límites: capacidad concentrada, dependencia del servidor y necesidad de escalar o replicar ese rol.

Un servidor no inicia espontáneamente una conexión cliente servidor, pero puede entregar novedades de varias formas:

  • Polling: el cliente pregunta periódicamente. Simple, con demora o tráfico inútil.
  • Long polling: el servidor retiene el pedido hasta tener novedad o vencer.
  • Streaming: una conexión iniciada por el cliente permanece abierta y transporta eventos.
  • Callback: el cliente ofrece otro endpoint y pasa a ser servidor para esa devolución.
Peer to peer. Participantes con roles equivalentes se descubren y se comunican directamente según un protocolo común.

P2P distribuye recursos y evita una autoridad de datos única, pero complica membresía, búsqueda, NAT, firewalls, confianza y consistencia. Un diseño híbrido suele usar registro central para discovery y conexiones directas para datos.

HTTP y REST

HTTP es un protocolo request response. Método, URL, headers y body forman el pedido; status, headers y body forman la respuesta. Es stateless a nivel de protocolo: cada pedido debe incluir el contexto necesario, aunque la aplicación pueda mantener sesión externa.

Una arquitectura REST respeta:

  • Cliente servidor: separación de interfaz y almacenamiento.
  • Stateless: cada request se interpreta por sí mismo.
  • Cache: las respuestas declaran si pueden reutilizarse.
  • Interfaz uniforme: recursos identificados por URI, representaciones, mensajes autodescriptivos e hipermedia cuando corresponde.
  • Sistema por capas: el cliente no necesita saber si habla con origen, proxy o cache.
  • Code on demand opcional: el servidor puede enviar código ejecutable.

La parte de hipermedia se conoce como HATEOAS: una representación incluye links a acciones o estados siguientes para que el cliente los descubra. Es parte de la definición académica de REST, aunque muchas APIs HTTP de producción no la implementan de forma completa.

Las URLs identifican entidades, no pantallas ni verbos arbitrarios: /orders/42. Relaciones se expresan con subrecursos o enlaces. El versionado puede estar en path, header o media type; la regla importante es hacer cambios aditivos y tolerar campos desconocidos antes de romper consumidores.

Semantic Versioning. Versión Major.Minor.Patch: Major cambia ante incompatibilidad de contrato, Minor agrega funcionalidad compatible y Patch corrige sin cambiar la interfaz.

Versionar la API no es versionar una entidad. La primera decisión permite que consumidores viejos convivan durante una migración. El versionado histórico conserva estados sucesivos del mismo recurso, por ejemplo revisiones de una página. Una API puede exponer /v2 y, dentro de ella, muchas revisiones de cada entidad.

RPC y gRPC

RPC. Abstracción que permite invocar un procedimiento remoto mediante una interfaz parecida a una llamada local.

Una IDL define operaciones y tipos sin depender del lenguaje. Un generador produce client stub y server stub. El stub cliente serializa argumentos, envía y espera. El servidor deserializa, invoca la implementación y serializa resultado o error. Marshalling incluye representación portable de tipos, endianness, strings y referencias.

aplicacion cliente
    -> client stub
        -> marshalling -> transporte -> unmarshalling

    <- resultado o error por el camino inverso

Fallos y call semantics

Si vence un timeout, el cliente no sabe si el servidor no recibió, ejecutó y perdió la respuesta, o sigue trabajando. Las semánticas posibles son:

  • Maybe: se intenta una vez, puede no ejecutarse.
  • At least once: se reintenta hasta observar respuesta, puede ejecutar varias veces.
  • At most once: se usan identificadores y cache de resultados para suprimir duplicados, puede no ejecutar si no se recupera.
  • Exactly once: requiere que efecto y registro de deduplicación sean atómicos y recuperables. No surge solo por usar RPC.

Las operaciones idempotentes toleran repeticiones respecto de su estado final. Para las demás, el cliente envía una idempotency key estable y el servidor persiste clave, estado y resultado.

Para trabajos de minutos no se deja una llamada bloqueada indefinidamente:

POST trabajo(idempotency_key) -> 202 {job_id}
GET  trabajo/{job_id}        -> pendiente | ejecutando | listo | error
GET  trabajo/{job_id}/resultado

gRPC usa contratos Protocol Buffers, generación de stubs y HTTP/2. Soporta llamada unaria, stream del servidor, stream del cliente y stream bidireccional. Deadlines y cancelación deben propagarse. Su interfaz orientada a procedimientos es útil entre servicios controlados, mientras REST suele ser más accesible para APIs web públicas.

Objetos distribuidos, CORBA y RMI

Un objeto distribuido expone identidad, estado y métodos remotos. Un middleware conserva referencias y enruta invocaciones. RPC llama procedimientos de un servicio; el modelo de objetos intenta extender semántica orientada a objetos a través de la red.

CORBA define IDL independiente del lenguaje, ORB para localizar objetos y transportar invocaciones, stubs, skeletons y servicios auxiliares. Java RMI aplica una idea similar dentro del ecosistema Java: interfaz remota, registry, stubs y serialización de objetos.

Patrones, middleware y mensajería

Los patrones de comunicación describen quién produce, quién recibe y qué acoplamiento existe en tiempo, espacio y cantidad. Un middleware implementa mecanismos comunes, pero las garantías finales dependen del protocolo completo, el almacenamiento y la lógica de aplicación.

Middleware y MOM

Middleware. Capa de software entre aplicación y plataforma que ofrece servicios comunes para comunicar, nombrar, serializar, asegurar y coordinar componentes heterogéneos.

Puede ser procedural (RPC), orientado a objetos, orientado a mensajes, transaccional o de datos. Sus objetivos son reducir acoplamiento, ocultar heterogeneidad, reutilizar mecanismos y ofrecer una política consistente de operación.

Un middleware centralizado concentra discovery, ruteo o persistencia en hosts conocidos. Facilita administración y observabilidad, pero concentra carga y fallos. Uno distribuido embebe agentes en los nodos y reparte esos servicios, con mayor escala y autonomía a costa de coordinación.

MOM. Middleware orientado a mensajes que desacopla productores y consumidores mediante canales, colas o tópicos y puede agregar ruteo, persistencia y confirmaciones.

Un bus de información distribuye eventos a suscriptores. Una cola entrega trabajo a consumidores, normalmente uno por mensaje. Un broker media direcciones, buffers y políticas. ZeroMQ ofrece abstracciones de mensajería sin imponer un broker central.

Grupos, difusión y atomicidad

Grupo de comunicación. Colección dinámica de procesos tratada como una entidad lógica, con primitivas para crear, unir, abandonar y enviar al conjunto.

Broadcast intenta alcanzar a todos en un dominio. Multicast alcanza a miembros de un grupo. Unicast tiene un destino. Anycast alcanza una instancia apropiada entre varias.

La membresía puede ser estática o dinámica. Con cambios dinámicos hace falta acordar vistas, altas, bajas y sospechas de fallo. Entrega atómica de grupo significa que el mensaje se entrega a todos los miembros correctos de una vista o a ninguno, no que cada handler sea transaccional.

Atomicidad de mensajes. Un mensaje dirigido a un grupo se entrega a todos los destinatarios de la vista acordada o no se entrega a ninguno.

Un middleware de grupos mantiene join(grupo, miembro), leave y send(grupo, mensaje). El servicio asigna una vista numerada, persiste o retransmite por miembro y entrega solo dentro de la vista acordada. Para atomicidad, un coordinador puede difundir, reunir ACK de todos y recién emitir DELIVER; si no llega a todos, emite ABORT. Esto cuesta dos rondas y puede bloquear ante fallos. Protocolos de reliable atomic multicast reemplazan el coordinador único con orden y acuerdo de vista.

Request Reply

Cada pedido necesita tipo, versión, request_id, operación y payload. La respuesta repite el identificador y lleva resultado o error. Sin correlación, varias operaciones en vuelo no pueden asociarse con su respuesta.

Para una operación asincrónica se pueden encadenar dos intercambios: el primero acepta y devuelve un ID, el segundo consulta o retira resultado. Esto evita mantener una conexión por toda la ejecución y permite persistir estado.

Producer Consumer

Varios consumidores compiten por mensajes de una cola. Cada unidad de trabajo debe ser suficientemente independiente. La cola absorbe ráfagas, pero no crea capacidad: si la tasa media de llegada supera a la de servicio, el backlog crece sin límite.

Backpressure se implementa con capacidad acotada, créditos, pausa de productores, rechazo o autoscaling con un límite. Orden estricto y paralelismo compiten: particionar por clave conserva orden dentro de cada clave y distribuye claves distintas.

Publisher Subscriber

Un publisher emite sin conocer suscriptores. Cada suscriptor interesado recibe una copia lógica. Un canal suele ser una dirección concreta; un tópico clasifica semánticamente y puede permitir patrones. Hay que definir retención, replay, posición del consumidor y conducta de suscriptores lentos.

Pipeline y DAG

Un pipeline procesa elementos en streaming: cuando una etapa termina el elemento A puede recibir B mientras la siguiente procesa A. El throughput queda limitado por la etapa más lenta. Replicarla requiere una política de reparto y, si importa el orden, una de recomposición.

Un DAG generaliza dependencias. Una tarea queda lista cuando completan todos sus predecesores. Si el grafo contiene un ciclo de espera no es DAG y puede haber deadlock. Conviene distinguir worker por etapa, especializado pero potencialmente ocioso, de worker por item, que ejecuta varias transformaciones y reduce transferencias.

ZeroMQ

ZeroMQ es una biblioteca de sockets con patrones de mensajería. Los procesos se conectan directamente o mediante un proxy construido con los mismos sockets. No ofrece por sí misma persistencia durable ni administración central.

bind crea un endpoint y connect se conecta a él. No equivalen necesariamente a servidor y cliente: un worker puede hacer connect hacia un ventilador central, mientras el patrón del socket define qué secuencias de mensajes son válidas. ZeroMQ transporta frames, pero la serialización y evolución del contenido quedan a cargo de la aplicación.

  • REQ REP: alternancia estricta request y reply. Simple, pero un peer caído bloquea el ciclo si no se diseña timeout y reconstrucción.
  • PUSH PULL: pipeline y distribución de trabajo. PUSH reparte, PULL recibe.
  • PUB SUB: difusión por prefijos. Un suscriptor que se conecta tarde pierde mensajes anteriores.
  • ROUTER DEALER: asincronismo y multiplexación. ROUTER conserva identidades para devolver a cada origen; permite construir broker y workers.
  • XPUB XSUB: proxy pub sub que hace visibles altas y bajas de suscripciones.

Barrera distribuida

Un coordinador conserva generación y conjunto de llegadas. La generación evita mezclar dos usos sucesivos:

worker:
    send ARRIVE(barrera_id, generacion, worker_id)
    esperar RELEASE(barrera_id, generacion)

coordinador al recibir ARRIVE:
    llegadas[generacion].add(worker_id)
    if size(llegadas[generacion]) == N:
        enviar RELEASE(generacion) a los N
        persistir generacion + 1

Con request reply, cada worker deja su request pendiente hasta liberar. Con MOM, ARRIVE entra a una cola y RELEASE puede publicarse a una cola por worker o tópico, con mensajes durables e idempotentes. Con blocking queues locales, cada worker pone un token y espera una señal propia. Deben definirse caída de un worker, timeout, participantes fijos y reutilización.

barrera correcta con blocking queues, N workers:
    arrivals = BlockingQueue()
    release[i] = BlockingQueue() para cada worker i

worker i:
    arrivals.put((generacion, i))
    if i == coordinador:
        vistos = set()
        while size(vistos) < N:
            (g, j) = arrivals.take()
            if g == generacion: vistos.add(j)
        for j in 0..N-1:
            release[j].put(generacion)
    release[i].take()

Una sola cola donde cada worker hace put y luego take no es barrera:
el primer take consume el primer put y cruza sin esperar a los demas.

Chat por grupos

Un chat de equipos modela cada equipo como grupo. La API mínima es join(team, player), publish(team, message_id, body), subscribe(team, offset) y leave. El servidor autoriza membresía, asigna secuencia por equipo, retiene historia según política y permite reanudar desde offset. El cliente deduplica por message_id. Presencia y chat son flujos distintos: perder un heartbeat no debe borrar mensajes.

Cola distribuida de turnos

Para que hasta diez agentes tomen el siguiente número de una fila, el estado autoritativo no puede ser una variable local en cada agente. Un servicio de turnos conserva ultimo_asignado en almacenamiento con incremento atómico y expone next(agent_id, request_id). La misma request_id devuelve el mismo turno si hay retry. Otra opción es precargar una cola durable y hacer que cada agente consuma con ACK, pero hay que decidir qué ocurre con un turno entregado si el agente cae antes de iniciar la llamada.

En ejercicios con mensajes, dibujá canal, dirección, cardinalidad y ACK. Después recorré el fallo entre “aplicar efecto” y “confirmar”: ahí aparece la necesidad de idempotencia.

Cómputo distribuido

Distribuir cómputo exige asignar trabajo, mover datos, detectar terminación y recuperarse. MapReduce, MPI, Flink y Beam eligen puntos distintos del espacio: batch tolerante a fallos, coordinación explícita de alto rendimiento, streaming con estado y modelo portable.

Coordinar actividades

Un coordinador debe responder:

  • qué tareas existen y cuáles están listas;
  • qué worker tiene cada tarea y qué lease limita esa asignación;
  • dónde viven input, estado intermedio y output;
  • cómo detectar caída sin confundirla con lentitud;
  • cuándo reintentar y cómo evitar doble efecto;
  • cómo saber que el trabajo global terminó.

La arquitectura master worker funciona bien cuando las tareas son independientes y el master maneja metadata, no todo el flujo de datos. Para evitar cuello de botella, los workers leen y escriben directamente en almacenamiento distribuido.

MapReduce

MapReduce. Modelo batch que transforma pares clave valor con una fase paralela map, agrupa por clave y aplica una fase reduce por grupo.
map(k1, v1)       -> lista de (k2, v2)
shuffle y sort    -> k2, [v2, v2, ...]
reduce(k2, vals)  -> lista de resultados
Contar palabras: map emite (palabra, 1) por aparición. Shuffle agrupa todos los unos de una palabra. reduce los suma.

Una ejecución típica:

  1. Particionar archivos de entrada en splits.
  2. Asignar cada split a un mapper, preferentemente cerca de sus datos.
  3. El mapper emite pares intermedios, los divide por reducer con una función de partición y materializa archivos intermedios locales para el shuffle.
  4. Un combiner opcional agrega localmente si la operación es asociativa y conmutativa.
  5. Shuffle transfiere cada partición al reducer correspondiente y sort agrupa claves.
  6. Cada reducer procesa una clave y escribe output durable.

Si un mapper cae se reejecuta porque su input es durable y su salida intermedia es regenerable. Si un reducer cae, se repite desde los intermedios. Tareas lentas pueden ejecutarse especulativamente en otro worker y aceptar el primer resultado. Esto exige funciones deterministas o efectos controlados.

MapReduce no es cualquier master worker. Su forma clave valor, shuffle y reejecución determinista son lo que permiten paralelizar y recuperar automáticamente.

Diseñar varias salidas

Para logs (email, url, fecha) se pueden ejecutar jobs o ramas:

navegaciones por dia:
    map:    emit(dia_semana(fecha), 1)
    reduce: emit(dia, sum(valores))

URL mas vista:
    map:    emit(url, 1)
    reduce: emit(url, sum(valores))
    job final: max por cantidad

emails con mas de 10:
    map:    emit(email, 1)

Calcular “más que la media global” suele requerir dos pasos: primero suma y cantidad global, luego filtrar entidades con ese umbral. Una condición de días consecutivos requiere que el reducer reciba todas las fechas de una cuenta, las ordene o las represente como conjunto y detecte adyacencia.

MPI y Open MPI

MPI. Estándar de pasaje de mensajes para programas paralelos donde procesos conocidos coordinan explícitamente comunicación punto a punto y colectiva.

Todos los procesos ejecutan el mismo programa en el modelo SPMD, pero usan su rank dentro de un communicator para tomar roles diferentes. El tamaño del communicator indica cuántos participan.

Las operaciones colectivas se invocan en el mismo orden desde todos los ranks del communicator. En Bcast, por ejemplo, el root aporta el buffer y los demás participan en la misma llamada para recibirlo. Saltear la colectiva en un rank puede bloquear al resto.

Apache Flink

Flink ejecuta dataflows con operadores y streams. Un batch es un stream acotado. Los operadores pueden mantener estado particionado por clave y procesar eventos continuamente.

Tiempo y ventanas

  • Processing time: reloj de la máquina que procesa. Baja latencia, resultado dependiente de demoras.
  • Event time: timestamp del evento. Permite reconstruir la semántica del origen aunque llegue tarde.
  • Ingestion time: timestamp al entrar al sistema, compromiso menos expresivo.

Una tumbling window divide intervalos sin solapamiento. Una sliding window solapa intervalos según tamaño y paso. Una session window agrupa actividad separada por gaps. Una ventana global requiere un trigger adicional.

Watermark. Estimación de que no llegarán eventos con event time menor que cierto valor. Permite cerrar ventanas tolerando un atraso configurado.

Los eventos más tardíos que el margen pueden descartarse, actualizar resultados o ir a una salida lateral. No existe un watermark perfecto sin esperar para siempre.

Arquitectura y recuperación

El JobManager coordina jobs, scheduling y checkpoints. TaskManagers ofrecen slots y ejecutan subtareas. Los operadores se encadenan cuando conviene para evitar serialización y red. keyBy particiona estado y eventos de una misma clave hacia la misma instancia lógica.

Los checkpoints insertan barreras en los streams. Cuando un operador recibió la barrera de todos sus inputs, captura un estado consistente y propaga. Ante caída, se restaura el último checkpoint y se reproducen fuentes capaces de replay. Exactly once respecto de un sink externo requiere un conector transaccional o idempotente, no solo checkpoint interno.

Apache Beam

Beam separa un modelo de programación de sus motores de ejecución. El programa construye un pipeline de PCollections y PTransforms. Un runner lo ejecuta sobre Flink, Spark, Dataflow u otro backend compatible.

  • Cuándo: qué trigger emite resultados.
  • Cómo: si cada emisión descarta o acumula resultados anteriores.

Escala, disponibilidad y cloud

Escalar significa sostener objetivos al crecer una dimensión de carga. Elasticidad agrega adaptación automática hacia arriba y hacia abajo. Alta disponibilidad exige eliminar dependencias cuyo fallo interrumpe el servicio. Cloud, microservicios y serverless son medios posibles, no sustitutos de esas definiciones.

Escalabilidad

Escalabilidad. Capacidad de conservar objetivos de servicio cuando crecen usuarios, datos, operaciones o distribución geográfica mediante una cantidad razonable de recursos.

La cátedra distingue tres dimensiones: tamaño, más usuarios, datos o recursos; geografía, mayor distancia y cantidad de ubicaciones; y administración, nuevas organizaciones, políticas, sintaxis, semánticas o servicios que deben interoperar. Un sistema puede escalar en una dimensión y fallar en otra.

Antes de elegir tecnología se identifica la dimensión que crece y el recurso limitante: CPU, memoria, disco, IOPS, ancho de banda, conexiones, locks, coordinador o capacidad de una partición.

Una instancia de aplicación stateless se replica con facilidad porque cualquier pedido puede ir a cualquiera. Sesión, archivos locales y jobs en memoria vuelven sticky al tráfico o exigen extraer estado a un sistema compartido. Esto no elimina estado, solo lo ubica donde puede escalar y recuperarse.

Una plataforma de alta concurrencia mantiene capacidad compartida para muchos pedidos breves. Un sistema ad hoc crea recursos para una tarea específica y los destruye al terminar. El primero amortiza arranque; el segundo aísla y ajusta recursos por trabajo.

Patrones de carga web

  • Estable: capacidad base y margen conocido.
  • Diario o periódico: preescalado antes del pico evita esperar métricas.
  • Flash crowd: CDN, cache, cola y límites absorben una subida abrupta mientras escala.
  • Crecimiento sostenido: partición y capacity planning, no solo autoscaling de frontend.
  • Trabajo costoso aislado: cola y workers separados impiden que una operación agote requests comunes.

Elasticidad como lazo de control

Elasticidad. Capacidad de ajustar recursos automáticamente según la carga, agregándolos cuando hacen falta y retirándolos cuando dejan de ser útiles.

Una arquitectura elástica necesita:

  1. Sensor: mide demanda o saturación, por ejemplo utilización, latencia o backlog.
  2. Controlador: compara contra un objetivo y decide capacidad deseada.
  3. Actuador: crea, elimina o reconfigura instancias.

Escalar por CPU sirve si CPU correlaciona con demanda. Para consumidores de cola suele convenir backlog por worker y antigüedad del mensaje más viejo. Hay que considerar tiempo de arranque, cooldown, histéresis, capacidad mínima y máxima. Sin histéresis, pequeñas variaciones producen oscilación.

En AWS, métricas y alarmas pueden alimentar Auto Scaling Groups y balanceadores. En Kubernetes, Horizontal Pod Autoscaler ajusta réplicas, scheduler asigna pods a nodos y Cluster Autoscaler ajusta nodos. Readiness evita enviar tráfico antes de estar listo; liveness reinicia un proceso trabado, y una mala configuración puede convertir lentitud transitoria en tormenta de reinicios.

Alta disponibilidad y confiabilidad

Availability. Fracción del tiempo en que el servicio está disponible: A = MTTF / (MTTF + MTTR).
Reliability. Probabilidad de operar correctamente sin interrupción durante un intervalo.

Disponibilidad mejora al fallar menos o reparar más rápido. Los “nueves” convierten porcentaje en presupuesto anual aproximado:

ObjetivoIndisponibilidad anual aproximada
99%3 días 15 horas
99.9%8 horas 46 minutos
99.99%52 minutos 36 segundos
99.999%5 minutos 15 segundos

Si componentes independientes están en serie y todos deben funcionar:

A_serie = A1 * A2 * ... * An

Si dos componentes independientes son redundantes y alcanza con uno:

A_paralelo = 1 - (1 - A1) * (1 - A2)
Dos instancias independientes de 99% en paralelo darían 99.99%. La cuenta deja de valer si comparten base, zona, configuración defectuosa o despliegue que las rompe juntas.

Un cluster necesita redundancia, detección y failover. Redundar sin un mecanismo para desviar tráfico no aumenta el servicio observable. También importan dominios de fallo independientes, capacidad de la réplica durante el failover y pruebas periódicas.

SLI, SLO y SLA

  • SLI: medición, por ejemplo proporción de requests válidos con latencia menor a 300 ms.
  • SLO: objetivo interno sobre un SLI, por ejemplo 99.95% mensual.
  • SLA: compromiso contractual y consecuencias si no se cumple.

El error budget es 1 - SLO. Permite equilibrar cambios y estabilidad. Un promedio de latencia oculta colas largas; se usan percentiles como p95 o p99.

Teorema CAP

Ante una partición de red entre réplicas, un sistema distribuido no puede garantizar simultáneamente:

  • Consistencia C: cada operación observa una única historia equivalente a una copia actualizada, en la interpretación usual de CAP.
  • Disponibilidad A: todo pedido a un nodo no fallado obtiene una respuesta no errónea.
  • Tolerancia a particiones P: el sistema sigue bajo pérdida arbitraria de mensajes entre grupos.

Cuando ocurre P, un lado puede rechazar operaciones para preservar C, o responder sin coordinar para preservar A y aceptar divergencia. Fuera de una partición se siguen negociando latencia y consistencia. CAP no dice que un sistema elige solo dos propiedades todo el tiempo ni que una réplica local lenta sea una partición.

Datos distribuidos

Distribuir datos combina tres decisiones distintas: modelo de almacenamiento, replicación y partición. Replicar mejora lecturas y tolerancia a fallos, particionar reparte capacidad, y cada combinación define consistencia, ruteo y recuperación.

Una base relacional ofrece esquema, relaciones, constraints y lenguaje de consulta general. NoSQL agrupa modelos clave valor, documentos, columnas anchas y grafos. La elección depende de accesos, invariantes y escala, no de una oposición entre “SQL lento” y “NoSQL rápido”.

  • Columnar: mantiene juntos valores de una columna. Comprime bien y lee solo columnas necesarias para analítica.

Replicación

Replicación. Mantener copias del mismo conjunto lógico para aumentar disponibilidad, cercanía o capacidad de lectura.

Leader based

Todas las escrituras pasan por un leader, que registra un orden y envía cambios a followers. Las lecturas pueden ir al leader para máxima actualidad o a followers aceptando lag. La replicación sincrónica espera una o más copias antes de confirmar; reduce pérdida ante fallo pero aumenta latencia y puede bloquear. La asincrónica confirma antes y admite perder cambios recientes si el leader cae.

El failover requiere detectar caída, elegir nuevo leader y redirigir. Un timeout demasiado corto produce elecciones innecesarias. Si dos lados aceptan escrituras como leader aparece split brain.

Multi leader

Varios leaders aceptan escrituras, útil entre regiones o clientes desconectados. Los cambios concurrentes pueden entrar en conflicto. Resolver por último timestamp puede perder datos y depende de relojes. Alternativas: merge específico del dominio, CRDT, conservar hermanos o asignar cada entidad a una región principal.

Leaderless y quorums

El cliente escribe a varias réplicas y lee varias. Con N copias, W confirmaciones de escritura y R respuestas de lectura:

si W + R > N, lectura y escritura intersectan al menos una replica
si W > N/2, dos escrituras de quorum intersectan

La intersección no garantiza por sí sola linearizabilidad: hay escrituras concurrentes, versiones, fallos y sloppy quorums. El lector elige la versión mediante números, vectores o reglas de conflicto y puede hacer read repair. Anti entropy compara réplicas en segundo plano.

Modelos de consistencia

  • Linearizable: cada operación parece ocurrir en un punto entre invocación y respuesta y respeta tiempo real.
  • Secuencial: existe un orden total consistente con el orden de cada proceso, no necesariamente con tiempo real.
  • Causal: todos respetan relaciones causales, operaciones concurrentes pueden verse en distinto orden.
  • Eventual: si cesan escrituras, las réplicas convergen, sin limitar cuánto tardan ni qué se lee antes.
  • Read your writes: un cliente no pierde de vista sus propias escrituras.
  • Monotonic reads: una vez vista una versión, el cliente no vuelve a una anterior.

La consistencia se especifica por operación y requisito. Un catálogo puede tolerar lectura atrasada; confirmar un pago o adquirir un lock suele requerir coordinación fuerte.

    ACK vuelve DN3 -> DN2 -> DN1 -> cliente

Los DataNodes envían heartbeats y reportes de bloques. Si uno cae, el NameNode ordena re replicar hasta recuperar el factor. Rack awareness ubica copias en dominios distintos. Los bloques grandes reducen metadata y favorecen throughput; el costo es desperdicio o metadata excesiva con archivos pequeños.

HDFS mueve cómputo hacia datos y tolera hardware commodity. No está pensado para baja latencia, millones de archivos diminutos ni escrituras aleatorias generales. Su consistencia y patrón write once o append son deliberadamente más restringidos que POSIX.

App Engine y BigTable

Google App Engine muestra cómo una PaaS fuerza aplicaciones replicables y administra versiones, instancias, colas y almacenamiento. BigTable muestra el soporte de datos: tabla dispersa, particionada por rangos y servida por tablet servers coordinados mediante metadata y Chubby.

PaaS en detalle

Una PaaS recibe código o un artefacto y administra runtime, aislamiento, despliegue, balanceo, escalado, health checks, logs y servicios asociados. Para poder crear y destruir instancias libremente, la aplicación debe:

  • no depender del disco local para estado durable;
  • responder pedidos dentro de límites;
  • usar servicios externos para datos, cache y colas;
  • tolerar múltiples instancias y reintentos;
  • declarar configuración y dependencias de modo reproducible.

La plataforma restringe para ganar capacidad de operación. El costo es menor control del host, límites de runtime y dependencia de APIs del proveedor.

Google App Engine

La jerarquía lógica es:

aplicacion
  servicio A
    version A1 -> instancias xN
    version A2 -> instancias xM
  servicio B
    version B1 -> instancias xK
  • Aplicación: unidad administrativa y de recursos.
  • Servicio: componente con configuración y escala propias.
  • Versión: artefacto desplegado e inmutable, útil para rollback y tráfico gradual.
  • Instancia: proceso concreto creado según demanda.

Un frontend recibe tráfico, resuelve aplicación, servicio y versión, y balancea entre instancias. El scheduler puede crear instancias por carga y retirarlas. Separar versión de instancia permite canary, blue green y rollback sin editar procesos vivos.

El entorno original restringía filesystem, sockets y duración para que cualquier request pudiera ejecutarse en cualquier instancia. Las tareas largas se enviaban a colas. Aunque los runtimes modernos sean más flexibles, la idea de diseño se conserva: estado durable fuera de la instancia.

Push, pull y leasing

En una push queue, la plataforma invoca un handler HTTP y reintenta si no obtiene éxito. El handler debe ser idempotente. Tasa, concurrencia y backoff protegen al servicio.

En una pull queue, workers piden tareas y reciben un lease. Durante el lease nadie más debería tomarlas. Si el worker termina, elimina la tarea. Si cae, el lease vence y otro la recibe. Un lease reduce ejecución simultánea, pero no evita duplicado si el worker produjo el efecto y cayó antes de borrar.

tarea disponible
    -> lease por T segundos
        -> exito: delete
        -> fallo o timeout: vuelve a disponible

Datastore y partición

Datastore ofrece entidades con key y propiedades sobre una infraestructura particionada. La clave determina identidad y ubicación. Los grupos de entidades permiten transacciones fuertes dentro de un alcance acotado, pero una raíz demasiado popular concentra escrituras.

La lección general es que el límite transaccional debe coincidir con el agregado del dominio. Una transacción global fácil de pedir es difícil de escalar. Índices permiten consultas, pero cada índice agrega escrituras y almacenamiento.

Modelo de BigTable

BigTable. Mapa ordenado, distribuido, persistente y disperso indexado por (row key, column key, timestamp).

Las filas se ordenan lexicográficamente por row key. Las columnas se agrupan en column families declaradas, mientras calificadores pueden aparecer dinámicamente. Cada celda conserva versiones por timestamp. “Disperso” significa que una celda inexistente no ocupa lugar.

(row_key, family:qualifier, timestamp) -> bytes

web.example/page42
  contenido:html  @t3 -> ...
  metricas:vistas @t5 -> 918
  links:a         @t2 -> destino

La row key domina localidad y carga. Campos que se consultan juntos conviene que queden en filas cercanas. Una clave monotónica concentra escrituras nuevas en el último rango. Se evita anteponiendo hash, bucket o identificador distribuido, aceptando que ciertas consultas por rango necesitarán fan out.

Tablets y jerarquía

Tablet. Rango contiguo de filas servido como unidad de partición y asignación.

La localización usa tres niveles conceptuales:

  1. Chubby conserva la ubicación del root tablet.
  2. El root tablet contiene ubicaciones de tablets de metadata.
  3. Las tablets de metadata indican qué tablet de usuario contiene una row key.

El cliente cachea ubicaciones. Si consulta el tablet equivocado, invalida y vuelve a resolver. La jerarquía evita un directorio central enorme en cada lookup.

Master, tablet servers y Chubby

  • Master: asigna tablets, detecta altas y bajas, balancea y coordina cambios de esquema. No está en el camino normal de cada lectura o escritura.
  • Tablet server: sirve tablets, mantiene memoria, logs y archivos persistentes, y divide tablets grandes.
  • Chubby: servicio de locks y archivos pequeños con consistencia fuerte, usado para elección de master, membresía y bootstrap.

Separar control y datos evita que el master sea cuello de botella de I/O. Si cae, los tablet servers pueden seguir sirviendo durante un período mientras se elige otro, aunque cambios de asignación se pausen.

Camino de escritura y lectura

Una escritura llega al tablet server, se agrega a un commit log durable y a una estructura en memoria. Cuando crece, se vuelca a archivos ordenados inmutables. Compactions combinan archivos y descartan versiones vencidas. Una lectura consulta memoria y archivos relevantes, ayudada por índices y filtros.

Cuando una tablet supera un umbral, se divide por rango. El master reasigna partes. El balance depende de que las row keys no concentren tráfico en una única tablet, aunque haya muchas máquinas libres.

En BigTable casi toda pregunta vuelve a la row key. Hay que poder dibujar la jerarquía Chubby, root, metadata, tablet y explicar por qué una clave monotónica crea hotspot.

Diseño de gran escala

Diseñar para un final no consiste en nombrar componentes conocidos. NALSD obliga a fijar números, límites, flujos y fallos para que cada caja del diagrama tenga una razón cuantitativa. Los casos prácticos de la materia se reducen a un método repetible.

Método NALSD

NALSD. Non Abstract Large System Design, diseño de gran escala basado en requisitos concretos, estimaciones y arquitectura física verificable.
  1. Scope: listar casos de uso incluidos y excluidos.
  2. SLO: latencia, disponibilidad, frescura, durabilidad y recuperación.
  3. Entidades y API: datos, identidad, relaciones y operaciones.
  4. Volumen: requests por segundo, bytes, retención, picos y crecimiento.
  5. Flujos: camino de escritura, lectura, procesamiento y errores.
  6. Arquitectura: componentes, partición, replicación, colas, caches y geografía.
  7. Fallos: recorrer duplicados, caída, retry, backlog, pérdida de zona y recuperación.
  8. Tradeoffs: declarar qué se prioriza y qué se acepta degradar.

Las estimaciones usan órdenes de magnitud. No buscan adivinar hardware exacto, sino revelar qué domina:

QPS_promedio = operaciones_por_dia / 86400
QPS_pico     = QPS_promedio * factor_pico
ingesta_dia  = eventos_dia * bytes_evento
storage      = ingesta_dia * retencion_dias * replicas * overhead
ancho_banda  = eventos_segundo * bytes_evento
workers      = QPS_pico * tiempo_servicio_segundos / utilizacion_objetivo
Si llegan 40.000 imágenes diarias de 650 KB, la ingesta ronda 26 GB por día, 9,5 TB por año antes de réplicas. El promedio es menor a 1 imagen por segundo, pero una salida laboral puede concentrar miles en minutos. Dimensionar solo por promedio es incorrecto.

Fallos, coordinación y transacciones

Tolerar fallos empieza por distinguir causa, estado incorrecto y servicio incorrecto. Después se elige detección, redundancia y recuperación. La coordinación distribuida agrega protocolos para exclusión y commit, pero ningún protocolo puede convertir una detección incierta en conocimiento perfecto.

Fallo, error y avería

Fallo parcial. Un componente falla mientras el resto del sistema sigue operando. Es la diferencia central respecto de un único programa que se detiene como conjunto.
Fault. Causa adjudicada o hipotética de un error, por ejemplo un bit alterado, un bug o un corte.
Error. Estado interno incorrecto que puede conducir a servicio incorrecto.
Failure o avería. Desviación observable del servicio respecto de su especificación.
fault se activa -> error interno -> cruza la frontera -> failure observable

Contener el error antes de la frontera evita que se convierta en avería. Un checksum detecta corrupción, una réplica puede enmascararla y una validación puede impedir propagarla.

Tolerancia a fallos. Capacidad de continuar con un comportamiento definido como aceptable en presencia de fallos. Puede significar servicio completo, degradación controlada o transición a un estado seguro.

Modelos de fallo

ClaseComportamientoEjemplo
CrashEl proceso deja de actuarHost apagado
Omisión de envíoNo emite un mensaje debidoBuffer o enlace descarta
Omisión de recepciónNo procesa un mensaje recibidoCola interna saturada

Un sistema puede ser sincrónico, parcialmente sincrónico o asincrónico según qué cotas conoce sobre cómputo, mensajes y relojes. El detector de fallos usa señales y timeouts, pero en un modelo asincrónico una ausencia de respuesta solo genera sospecha. La exactitud y rapidez del detector compiten.

Por persistencia, un fallo puede ser transiente, aparece una vez y desaparece; intermitente, aparece y desaparece de forma recurrente; o permanente, continúa hasta reparar o reemplazar. La estrategia cambia: retry puede resolver uno transiente, ocultar uno intermitente y empeorar la carga, y no corrige uno permanente.

Manejo de fallos

  • Prevención: reducir faults mediante diseño, tipos, pruebas y operación.
  • Eliminación: encontrar y corregir faults antes o después del despliegue.
  • Predicción: estimar tasa, consecuencias y riesgo.
  • Tolerancia: mantener servicio aceptable aunque el fault ocurra.

La tolerancia combina detección, confinamiento, enmascaramiento, reconfiguración y recuperación. Resiliencia es adaptarse y recuperar capacidad. Degradación suave conserva funciones esenciales y reduce otras, por ejemplo servir lecturas y rechazar escrituras durante una pérdida de quorum.

Redundancia y replicación operativa

EsquemaEjecuciónFailoverTradeoff
Pasiva, primary backupPrimary procesa y transfiere estadoBackup toma controlSimple, con demora y posible estado perdido
Activa, state machine replicationTodas procesan las mismas operaciones ordenadasOtra ya tiene el resultadoRápida, exige determinismo y orden total

  • Pasiva: usa menos cómputo y permite implementación no determinista, pero el backup puede quedar atrasado y el failover demora mientras recupera estado.
  • Activa: failover casi inmediato y comparación de respuestas puede detectar divergencia, pero todas las réplicas gastan cómputo, deben recibir orden total y ejecutar determinísticamente.
  • Semi activa: followers mantienen un log actualizado sin responder normalmente. Reduce el tiempo de recuperación, pero todavía necesita elección de leader y evitar split brain.

Redundancia espacial usa componentes simultáneos. Redundancia temporal reintenta. Redundancia de información agrega checksum o códigos. Réplicas idénticas no protegen contra el mismo bug o configuración: safety crítica puede exigir diversidad de diseño.

Recuperación y dependability

  • Backward recovery: volver a un checkpoint consistente y reproducir.
  • Forward recovery: transformar el estado erróneo en uno válido y continuar.
  • Log y replay: reconstruir estado aplicando operaciones durables.
  • Infraestructura inmutable: reemplazar una instancia por una conocida en vez de repararla manualmente.

RPO mide cuántos datos se acepta perder en tiempo. RTO mide cuánto puede tardar la restauración. Backup sin restauración probada no demuestra recuperación. Disaster recovery debe cubrir credenciales, configuración, dependencias externas y procedimientos, no solo archivos.

Un sistema dependable se evalúa por:

  • Availability: probabilidad de estar operando en un instante.
  • Reliability: continuidad de servicio correcto durante un intervalo. Un sistema siempre encendido que alterna respuestas actuales y viejas puede estar disponible pero ser poco fiable.
  • Durability: probabilidad de recuperar un dato que el sistema confirmó como persistido.
  • Safety: ausencia de consecuencias catastróficas cuando falla, no seguridad contra atacantes.
  • Maintainability: facilidad y tiempo necesarios para reparar, actualizar o restaurar.

Exclusión mutua distribuida

El objetivo es que un solo proceso acceda a un recurso crítico, con progreso y, si se pide, orden justo. No hay memoria compartida para un mutex.

Servidor central

Los procesos envían REQUEST a un coordinador. Si está libre, responde GRANT; si no, encola. Al salir reciben RELEASE. Usa tres mensajes por entrada y es fácil de razonar, pero el coordinador es cuello y dominio de fallo. Hay que recuperar quién tenía el lock y evitar dos coordinadores activos.

Token ring

Un token circula por un anillo lógico. Quien lo posee puede entrar y luego lo pasa. Garantiza exclusión y espera acotada si el anillo funciona. Perder token requiere regenerarlo sin crear dos; caer un nodo requiere reconstruir sucesores.

Ricart y Agrawala

Cada proceso timestampa su pedido con reloj de Lamport y lo envía a todos. Un receptor responde de inmediato si no quiere entrar o si el pedido ajeno tiene menor par (timestamp, id); en otro caso difiere la respuesta. El solicitante entra al recibir respuesta de los otros N - 1.

solicitar:
    estado = WANTED
    pedido = (lamport++, mi_id)
    enviar REQUEST(pedido) a todos
    esperar REPLY de todos
    estado = HELD

recibir REQUEST(r):
    if estado == HELD or (estado == WANTED and mi_pedido < r):
        diferir(r.origen)
    else:
        enviar REPLY

liberar:
    estado = RELEASED
    responder a diferidos

Cuesta 2(N - 1) mensajes y la caída de un participante puede bloquear si se espera a todos. La comparación total rompe empates y preserva orden.

Two Phase Commit

2PC. Protocolo de atomic commit en el que un coordinador pregunta si todos pueden confirmar y luego comunica una decisión global commit o abort.
Fase 1, prepare:
  coordinador -> PREPARE a participantes
  participante:
      valida y fuerza estado PREPARED en log
      responde YES
      o responde NO y aborta

Fase 2, decision:
  si todos YES: coordinador fuerza COMMIT y lo envia
  si algun NO o timeout antes de decidir: fuerza ABORT y lo envia
  participantes registran decision, liberan locks y confirman

Un participante que votó YES prometió poder confirmar después de reiniciar, por eso persiste cambios y conserva locks. Si queda PREPARED y pierde contacto con el coordinador, no puede decidir unilateralmente: podría contradecir un commit ya decidido. 2PC es bloqueante.

FalloRecuperación
Participante antes de votar YESAl recuperar puede abortar
Participante después de YESConsulta decisión, permanece bloqueado si no la conoce
Coordinador antes de decisión durableRecupera log y puede abortar según estado
Coordinador después de decisión durableReenvía la misma decisión

2PC no es consenso tolerante a particiones: presupone recuperación del coordinador o acceso a su decisión. Una saga evita locks largos dividiendo en transacciones locales y compensaciones, pero ofrece una semántica de negocio distinta de atomicidad ACID global.

Para dibujar 2PC, incluí logs durables y el estado PREPARED. Si solo aparecen mensajes YES y COMMIT, falta explicar por qué un nodo puede cumplir su voto después de caer.

Tiempo, orden y snapshots

Los relojes físicos aproximan tiempo real, los lógicos representan causalidad. A partir de causalidad se definen órdenes de entrega y cortes consistentes. Esta sección desarrolla algoritmos y condiciones, porque son preguntas centrales de final.

Relojes físicos, drift y skew

Tiempo. Magnitud usada para medir duración y separación entre eventos. En cómputo se modela de forma discreta y monotónica: una fuente usada para duraciones no debe retroceder.
Drift. Diferencia entre la velocidad de un reloj y la del tiempo ideal.
Skew. Diferencia instantánea entre dos lecturas de reloj.

Si la tasa de drift está acotada por rho, dos relojes que se sincronizaron juntos pueden separarse hasta aproximadamente 2 * rho * tiempo. Para mantener skew menor que delta hay que resincronizar antes de delta / (2 * rho).

Ajustar el reloj hacia atrás puede romper timers y orden local. Los sistemas suelen corregir gradualmente la velocidad, slewing, o separar reloj monotónico para duraciones de reloj de pared para fechas.

Algoritmo de Cristian

El cliente envía en t0, el servidor responde con su tiempo Ts y el cliente recibe en t1. Si la demora es simétrica y el procesamiento es despreciable:

RTT = t1 - t0
tiempo_estimado_al_recibir = Ts + RTT/2
incertidumbre aproximada = RTT/2

Se repite y se prefiere la muestra con menor RTT, porque probablemente tuvo menos cola. Si ida y vuelta son asimétricas, el error puede acercarse a esa asimetría.

NTP

NTP. Protocolo para sincronizar muchos relojes contra UTC con tolerancia a demoras y caídas, diseñado para sincronización, alta disponibilidad y escalabilidad.

Con cuatro timestamps, t1 salida cliente, t2 recepción servidor, t3 salida servidor y t4 recepción cliente:

offset theta = ((t2 - t1) + (t3 - t4)) / 2
delay  delta = (t4 - t1) - (t3 - t2)

NTP organiza servidores en estratos: 0 son fuentes físicas como GPS o relojes atómicos, 1 se conecta directamente a ellas y cada estrato N se sincroniza con fuentes de N menos 1. Los peers del mismo estrato pueden darse backup mutuo. Modos: cliente servidor, simétrico entre peers y broadcast o multicast con menor precisión.

La tolerancia a fallos no depende de una sola medición: usa servidores y rutas redundantes, consulta varias fuentes, descarta muestras dispersas o con RTT alto y cambia de fuente si una se vuelve inválida. Usa UDP 123 porque una medición perdida se reemplaza por otra y retransmitir alteraría la demora que se intenta estimar.

Eventos y happened before

Happened before. Relación a -> b si ambos eventos pertenecen al mismo proceso y a ocurre antes, si a es envío y b su recepción, o por transitividad.

Si no vale a -> b ni b -> a, son concurrentes. Causalidad es un orden parcial: algunos pares son comparables y otros no.

Relojes de Lamport

antes de cada evento local o envio:
    C = C + 1
    si envia, adjunta C

al recibir timestamp T:
    C = max(C, T) + 1

Garantiza a -> b implica L(a) < L(b). La inversa no vale: timestamps distintos no prueban causalidad. Para obtener un orden total operativo se compara (L(evento), process_id), pero ese desempate ordena también eventos concurrentes.

Vectores de relojes

Cada proceso i mantiene un vector de N componentes:

evento local o envio en i:
    V[i] = V[i] + 1
    adjuntar V

recepcion en i de vector W:
    para cada k: V[k] = max(V[k], W[k])
    V[i] = V[i] + 1

Se define V < W si todos los componentes de V son menores o iguales y al menos uno es menor. Entonces:

a -> b  si y solo si  V(a) < V(b)
a || b  si V(a) y V(b) son incomparables

Lamport cuesta un entero por mensaje y no detecta concurrencia. Vectores cuestan N y requieren gestionar membresía, pero capturan causalidad exactamente.

En tres procesos, a = [1,0,0] y b = [2,1,0]: a < b, por lo tanto a ocurrió antes que b. En cambio c = [2,1,0] y d = [1,0,1] son incomparables: c supera a d en los dos primeros componentes y d supera a c en el tercero, por lo tanto son concurrentes. Para reconstruir un diagrama, cada incremento identifica un evento local y un salto en otro componente revela información recibida mediante un mensaje.

Sincronismo de comunicación

Sincronismo distribuido. Un protocolo es sincrónico si sus acciones tienen cotas temporales conocidas; parcialmente sincrónico si las cotas existen pero se desconocen o aparecen después de un momento incierto; asincrónico si no se presupone una cota.
Steadiness, sigma. Máxima diferencia entre el mayor y el menor tiempo de delivery observado por un proceso: sigma = max(TDmax - TDmin). Mide qué tan regular es su recepción.
Tightness, tau. Máxima diferencia entre los tiempos de delivery del mismo mensaje en dos receptores: tau = max |tD_p(m) - tD_q(m)|. Mide qué tan simultáneamente lo observan.

Steadiness compara mensajes diferentes desde el punto de vista de un receptor. Tightness compara receptores para el mismo mensaje. Un flujo puede llegar regularmente a cada nodo y, sin embargo, con mucha diferencia entre nodos.

Delivery. Procesamiento de un mensaje por la aplicación, eventualmente con cambio de estado. Es distinto de la recepción física por el nodo.

Una hold back queue retiene mensajes recibidos hasta satisfacer la condición del orden.

Estado global y cortes

Estado local. Tupla de todas las variables internas de un proceso en un punto de su historia.
Estado global. Unión de los estados locales de todos los procesos y el estado de los canales, formado por mensajes enviados pero todavía no entregados.
Historia. Secuencia de eventos procesados por un proceso considerado como máquina de estados.
Corte. Unión de un prefijo de la historia de cada proceso. Su frontera contiene el último evento incluido de cada proceso.
Corte consistente. Si contiene un evento, contiene todas sus causas. En particular, no contiene una recepción sin contener el envío correspondiente.

Puede contener un envío sin recepción: el mensaje está en tránsito y pertenece al estado del canal. Un corte inconsistente describe un estado global imposible.

P0 tiene $100, descuenta $10 y envía una transferencia a P1, que parte de $0 y acredita al recibir. {P0: 90, P1: 0, canal: $10} es válido. {P0: 100, P1: 10} es inválido: contiene la recepción sin el envío y crea dinero sin causa.

Snapshot de Chandy y Lamport

Supuestos: canales confiables FIFO, procesos que no se detienen y grafo conectado.

iniciador:
    guardar estado local
    enviar MARKER por todos los canales salientes
    comenzar a registrar mensajes de cada canal entrante

al recibir primer MARKER por canal c:
    si aun no guardo estado:
        guardar estado local
        estado(c) = vacio
        enviar MARKER por salientes
        registrar otros canales entrantes
    si ya habia guardado:
        estado(c) = mensajes registrados en c
        dejar de registrar c

termina cuando cada proceso recibio MARKER por todos sus canales entrantes

FIFO garantiza que los mensajes previos al marker por un canal llegan antes que él. En el canal que trae el primer marker, no puede quedar un mensaje pre snapshot por registrar. El algoritmo no congela el sistema: captura un corte consistente mientras continúa.

Usos: checkpoint distribuido, detectar terminación, deadlock, tokens perdidos y propiedades estables. Después hay que recolectar estados locales y de canal para analizarlos.

Comunicación confiable. Garantiza integridad, los datos no llegan corruptos; validez, lo entregado corresponde a lo enviado; y atomicidad de delivery, el mensaje se entrega completo y, en grupos, a todos los destinatarios acordados o a ninguno.
En Lamport, nunca afirmar la inversa. En snapshots, dibujá al menos un mensaje en tránsito y explicá por qué una recepción sin envío vuelve inconsistente al corte.

Consenso y elección de líder

Consenso hace que procesos correctos decidan un mismo valor pese a fallos. Elegir líder resuelve quién coordina durante una época, pero no alcanza para preservar decisiones entre líderes. Paxos y Raft combinan quorums, términos y logs para conservar safety durante cambios.

Elección de líder

Elección de líder. Algoritmo que selecciona un proceso del grupo para un rol particular y permite reelegir cuando el líder se retira o falla.

Propiedades esperadas:

  • Safety: a lo sumo un líder válido por término o vista.
  • Liveness: si existe suficiente conectividad, finalmente se elige uno.
  • Acuerdo: procesos correctos reconocen al mismo líder y término.
  • Unicidad de identidad: los candidatos se comparan sin empate.

Un detector basado en timeout puede iniciar elecciones aunque el líder siga vivo pero aislado. Por eso cada autoridad lleva un número de término y una operación se acepta solo bajo reglas que impiden dos términos activos sobre el mismo estado.

Algoritmo del anillo

Los procesos forman un anillo lógico y tienen IDs únicos. Al sospechar al líder, un proceso envía ELECTION con su ID. Cada receptor agrega o conserva el máximo y reenvía. Cuando el mensaje vuelve al iniciador, el máximo es líder y circula COORDINATOR.

P2 -> P3 -> P4 -> P1 -> P2
ELECTION: max visto hasta recorrer el anillo
COORDINATOR(max_id): segunda vuelta para informar

Puede costar O(N) mensajes con mensaje de máximo o O(N cuadrado) en variantes donde cada candidato circula. Dos elecciones simultáneas convergen al mismo máximo si mensajes y membresía se manejan correctamente. Caídas exigen saltar al siguiente vivo y reparar el anillo.

Bully algorithm

Al detectar que el coordinador no responde, un proceso envía ELECTION a todos con ID mayor. Si nadie responde, se proclama y envía COORDINATOR a los menores. Si responde alguno, el iniciador se retira y uno mayor continúa. Al recuperarse, un proceso alto puede iniciar elección y desplazar al actual.

En el peor caso genera O(N cuadrado) mensajes. Presupone conocer a todos y poder contactarlos. El mayor ID gana, no el más capaz salvo que el ID codifique esa política.

Problema del consenso

Consenso. Dado un conjunto de procesos y un punto de decisión, todos los procesos correctos deben acordar el mismo valor.

Cada proceso propone un valor y debe decidir:

  • Agreement: procesos correctos no deciden distinto.
  • Validity: el valor decidido fue propuesto o cumple la regla de validez.
  • Integrity: cada proceso decide a lo sumo una vez.
  • Termination: procesos correctos finalmente deciden.

En un sistema completamente asincrónico con al menos un posible crash, ningún algoritmo determinista garantiza siempre termination. Los protocolos prácticos preservan safety sin tiempo y obtienen liveness bajo sincronía parcial, timeouts y períodos estables.

Quorum de mayoría. Para tolerar f caídas y todavía decidir por mayoría se requieren al menos N = 2f + 1 procesos. Cualquier par de mayorías se intersecta.

Consenso sincrónico por rondas

Si se conoce una cota de f crashes y las rondas tienen entrega acotada, cada proceso difunde los valores conocidos durante f + 1 rondas. La ronda extra permite que un valor recibido justo antes de caer se propague. Al final todos aplican la misma función determinista, por ejemplo mínimo.

known = {mi_propuesta}
por ronda 1 hasta f + 1:
    enviar known a todos
    known = union(known, conjuntos_recibidos)
decidir min(known)

La prueba depende de rondas y límites conocidos. Sin ellos, no recibir en una ronda no distingue crash de demora.

Generales bizantinos

Falla bizantina. Comportamiento arbitrario en tiempo y respuesta, incluso enviando información diferente a participantes distintos o actuando de forma maliciosa.

Un participante bizantino puede mentir, omitir o enviar valores diferentes. En el problema clásico de mensajes orales sin firmas, para tolerar f traidores hacen falta:

N >= 3f + 1
Quorum bizantino. Para tolerar f procesos bizantinos en el modelo clásico se requieren al menos 3f + 1 procesos, de los cuales al menos 2f + 1 son correctos.

Con tres generales y un traidor, los leales no pueden distinguir si el comandante mintió o el mensajero alteró. Con cuatro y uno, cada general reenvía lo que recibió y la mayoría permite filtrar una versión inconsistente.

El algoritmo OM(f) reenvía recursivamente valores por caminos de longitud hasta f + 1 y aplica mayoría. Su costo crece rápidamente. Firmas digitales cambian supuestos porque un traidor no puede falsificar lo dicho por otro, aunque todavía puede omitir.

Tolerar crash con mayoría de 2f + 1 réplicas no equivale a tolerar Byzantine. Con actores arbitrarios, la cota clásica es 3f + 1.

Ejemplo paso a paso

Cuatro servicios miden 1010, 1000, 1000, 1030. Un algoritmo válido debe declarar la función de decisión. En una ronda sin fallos, cada uno difunde (id, medición), espera los cuatro valores y aplica mediana inferior o mayoría de valor si existe. Con mediana ordena [1000, 1000, 1010, 1030] y todos deciden 1000 por la misma regla. Si se tolera un crash en rondas sincrónicas, se propagan conjuntos durante dos rondas antes de decidir. El protocolo acuerda un valor, no demuestra que el sensor sea físicamente correcto.

Paxos

Paxos. Protocolo de consenso que elige un único valor entre propuestas concurrentes mientras pueda comunicarse una mayoría de acceptors.

Paxos decide un valor por instancia. Roles lógicos:

  • Proposer: propone número y valor.
  • Acceptor: participa en quorums y conserva promesas y aceptaciones.
  • Learner: aprende el valor elegido.

Un número de propuesta es único y totalmente ordenado, por ejemplo (contador, proposer_id). Una mayoría de acceptors forma quorum. Dos mayorías intersectan, base de la safety.

Fase 1, prepare y promise

proposer elige n y envia PREPARE(n)

acceptor al recibir:
    si n > mayor_prometido:
        persistir mayor_prometido = n
        responder PROMISE(n, ultima_aceptada_n, ultima_aceptada_valor)
    si no:
        rechazar o informar mayor_prometido

La promesa significa no aceptar propuestas futuras menores que n. La respuesta incluye el último par aceptado para que un proposer nuevo preserve una elección que pudo haber ocurrido aunque el proposer anterior haya caído.

Fase 2, accept y accepted

al reunir PROMISE de mayoria:
    si alguna respuesta trae valor aceptado:
        v = valor con mayor numero aceptado informado
    si no:
        v = mi valor
    enviar ACCEPT(n, v)

acceptor:
    si n >= mayor_prometido:
        persistir aceptada = (n, v)
        responder ACCEPTED(n, v)

El valor queda chosen cuando una mayoría lo acepta. Que un proposer reciba mayoría es una forma de enterarse, no lo que crea la elección. Si luego aparece número mayor, la regla de adoptar el valor aceptado con mayor número mantiene el mismo valor.

Dos proposers pueden interrumpirse con números crecientes y no avanzar. Un líder estable ejecuta prepare una vez y propone posiciones sucesivas, Multi Paxos. Paxos garantiza safety con mensajes demorados o duplicados; liveness requiere conectividad de quorum y competencia controlada.

Raft

Raft replica un log mediante roles follower, candidate y leader, divididos en términos crecientes.

Elección

  1. Followers reciben heartbeats del leader.
  2. Al vencer un timeout aleatorio, uno incrementa término, vota por sí mismo y pide votos.
  3. Cada nodo vota como máximo una vez por término y solo por un candidato cuyo log esté al menos tan actualizado.
  4. Con mayoría, el candidato es leader y envía heartbeats.

Timeouts aleatorios reducen empates. Un mensaje con término mayor obliga a bajar a follower.

Replicación y commit

El leader recibe un comando, lo agrega a su log y envía AppendEntries con índice y término del entry anterior. Si el follower no coincide, rechaza y el leader retrocede hasta encontrar prefijo común, luego reemplaza el sufijo conflictivo.

Una entrada del término actual queda committed cuando está almacenada en mayoría. El leader avanza commitIndex y las máquinas de estado aplican en orden. Entries anteriores quedan comprometidas indirectamente. La restricción de voto sobre log actualizado evita elegir un leader que perdió entradas committed.

Sistemas de tiempo real

En tiempo real, una respuesta correcta fuera de plazo es incorrecta. El objetivo principal es previsibilidad: acotar ejecución, comunicación y recuperación. El lazo de control conecta software con un proceso físico, por eso una demora puede tener consecuencias materiales.

Hard y soft real time

Sistema de tiempo real. Sistema cuya corrección depende del resultado lógico y del instante en que se produce.
  • Hard RT: incumplir un deadline es una falla del sistema, potencialmente catastrófica.
  • Soft RT: un incumplimiento degrada calidad o valor, pero puede tolerarse ocasionalmente.

Performance promedio alta no implica tiempo real. Una tarea de 1 ms promedio con pausas impredecibles de 1 s no sirve para un deadline de 10 ms. Importan WCET, latencia máxima, jitter, blocking y distribución de prioridades.

Comunicación previsible

Ethernet convencional y colas compartidas tienen contención variable. Un diseño RT necesita cotas o reserva:

  • prioridades y colas acotadas;
  • admisión de carga para no prometer más de lo ejecutable;
  • slots temporales como TDMA;
  • redundancia de red y caminos deterministas;
  • sincronización de relojes con error conocido;
  • timeouts derivados del deadline, no valores arbitrarios.

Un retry puede mejorar probabilidad de entrega pero consumir el tiempo restante. La política correcta pregunta cuántos intentos caben antes del deadline y qué modo seguro se activa si no alcanzan.

Arquitecturas industriales

La automatización clásica usa niveles: sensores y actuadores, controladores PLC, supervisión SCADA, ejecución de manufactura y planificación empresarial. Los niveles bajos requieren tiempos más estrictos y redes deterministas como fieldbus, Profibus o Profinet; los altos agregan y planifican. Ethernet o TCP sin una política temporal adicional no garantizan deadline solo por ser rápidos.

En automoción, una arquitectura distribuida por función conecta muchas ECUs. Una arquitectura zonal agrupa dispositivos por ubicación física en controladores de zona y lleva backbone de alta velocidad hacia cómputo central. Reduce cableado y consolida cómputo, pero vuelve críticos backbone y controladores centrales, que deben redundarse y aislarse.

Elementos:

  • Setpoint: valor deseado.

En lazo abierto no se mide resultado, por lo que no se corrigen perturbaciones. En lazo cerrado la realimentación ajusta el error. Muestrear demasiado lento pierde dinámica. Demora y jitter pueden volver inestable un controlador que matemáticamente funcionaba sin red.

Programación y scheduling

Una tarea RT debe tener ejecución acotada: evitar memoria dinámica impredecible, page faults, locks sin cota, I/O desconocido y garbage collection no controlado. Las interrupciones y drivers también consumen presupuesto.

Un backoff exponencial sin cantidad máxima es incompatible con hard RT porque no tiene peor caso finito útil. Si se permiten retries, cantidad, timeout y demora deben caber explícitamente dentro del deadline y terminar en una acción segura.

Inversión de prioridades. Una tarea alta queda bloqueada por un lock de una baja, mientras tareas medias impiden que la baja ejecute y libere.

Priority inheritance eleva temporalmente la prioridad de quien retiene el recurso. Priority ceiling asigna un techo a recursos y limita bloqueos de forma más analizable.

En un conjunto periódico simple, utilización es U = suma(Ci / Ti), donde Ci es WCET y Ti período. Que U < 1 es necesario en un procesador, pero no siempre suficiente bajo cualquier scheduler y blocking. La prueba real incluye deadlines, prioridades, interferencia y secciones críticas.

Fallos temporales y estado seguro

Un resultado tardío puede descartarse, porque aplicarlo después puede ser peor que omitirlo. Watchdogs detectan ausencia de progreso. Redundancia temporal solo sirve si el retry cabe. Redundancia espacial puede votar, pero las réplicas deben recibir datos comparables dentro de una ventana.

Un sistema safety critical define fail safe, estado seguro ante fallo, y fail operational, continuidad durante cierta cantidad de fallos. Frenar puede ser seguro para una máquina industrial y peligroso para un avión, por lo que “apagarse” no es una política universal.

Casos que fijan las ideas

Mars Pathfinder

Una tarea de alta prioridad esperaba un mutex retenido por una baja, mientras una media desplazaba a la baja. El watchdog reiniciaba el sistema. Habilitar priority inheritance permitió que la baja heredara prioridad, liberara y dejara avanzar a la alta.

Therac 25

Condiciones de carrera, overflow y confianza excesiva en software permitieron dosis peligrosas. Versiones anteriores tenían interlocks de hardware. La lección es defensa en profundidad: software concurrente no debe ser la única barrera contra una acción física catastrófica.

Ariane 5

Una conversión numérica fuera de rango en software reutilizado apagó sistemas redundantes que ejecutaban el mismo código y recibían el mismo dato. Redundancia idéntica no cubre fallos de diseño comunes. También deben revisarse supuestos al cambiar el contexto de uso.

Mt. Gox como contraste

No fue un caso RT, pero muestra que un error sin reconciliación ni mecanismo independiente de detección puede acumularse. Observabilidad y auditoría forman parte de la tolerancia: detectar tarde convierte un fallo pequeño en pérdida sistémica.

La respuesta central de tiempo real es “previsible, no necesariamente rápido”. Toda arquitectura debe mostrar deadline, peor caso, política de scheduling, comunicación y estado seguro.
